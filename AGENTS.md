# github-actions-toolkit

## What this is

The platform binding for outernet-foundation repos: everything that knows GitHub Actions exists. Renamed from `release-devkit` (the GitHub repo is renamed; redirects cover old URLs — the stale-spelling lint is gone, ruled out with the migration bridge over and the fleet operator-owned; the residual redirect risk, org-internal name reuse, is accepted). It holds the reusable workflows every consumer composes (`rebase`, `preflight`, `mirror`, `build-unity`, `compile-check-unity`, `build-docker`, `release-pr-builds`, `merge-if-ready`, `retry`, `cleanup-pr-releases`), the release composite action, the delivery verbs (release orchestration, per-package version tags, path-diff change detection, ephemeral version patching, OIDC trusted publishing), the merge verbs (`rebase`, `merge-if-ready`, `retry` — the rerun merge system of `adr-integrate-rerun-lander.md`), the matrix helper (fanout envelope plus per-leg base-version stamping), the closed-PR release sweep, and runner provisioning (absorbed from ci-devkit's `setup` with the vendored `third-party/` scripts). It must stay a project dependency of nothing — `bashrun` and `build-artifact-registry` are its runtime deps, so a project-level edge in any tool repo is a resolver cycle. Consumers reference it only through `uses:` at a full commit SHA; the code resolves from the consumer-side installs the reusables make.

The Python package/distribution is `github-actions-toolkit`/`github_actions_toolkit` (console-script names are the public API — under the stable-CLI-API doctrine the frozen surface is what consumer YAML spells, and no consumer YAML names a verb), and the consumer-owned root config file is `publish.yml`.

The consumer owns everything declarative — package and app identities, paths, registry mappings, the builds shelf each app's release assets pull from — in a root `publish.yml`; every command reads it. Per-repo copies of this machinery are refused, as are per-ecosystem splits — the seam is internal: one `Registry` adapter per registry over the shared tags/diff/versioning core. Registry primitives (ORAS push/pull, the builds shelf, `setup_oras`, `registry_auth`) live in [`build-artifact-registry`](https://github.com/outernet-foundation/build-artifact-registry), a PyPI dependency; this repo owns no ORAS code.

## Installation and invocation

Consumers never clone this repo themselves. A consumer workflow references a reusable (`uses: outernet-foundation/github-actions-toolkit/.github/workflows/<file>.yml@<full-sha>`) or the release composite (`uses: outernet-foundation/github-actions-toolkit/.github/actions/release@<full-sha>` with `channel: dev` or `channel: stable`); the `@sha` is the whole version control. Third-party action SHAs are pinned once, inside this repo's files — consumers pin nothing but this repo.

The install trio lives in three composite actions referenced via the `$/` self-repository syntax (`uses: $/.github/actions/checkout`, `toolkit-checkout`, `setup-uv`) — `$` resolves to this repository at the commit the caller pinned, so the composites are single-copy across every reusable and can never drift from the pin. Where a job runs binding verbs, `toolkit-checkout` comes first: a hand-spelled git fetch (`git init` → `remote add` → `fetch --depth 1 origin <sha>` → `checkout --detach FETCH_HEAD`) at `job.workflow_repository`/`job.workflow_sha` — exactly the SHA the caller spelled — into `${{ runner.temp }}/github-actions-toolkit`, never the workspace: a nested clone would be wiped by `checkout`'s `git clean -ffdx` and scanned by the consumer's zizmor/deptry, and `actions/checkout` cannot make this clone anyway — it refuses any `path` outside `$GITHUB_WORKSPACE` (actions/checkout#197, every release since v2). The org is public, so the fetch carries no token (nothing can ever persist credentials — same shape as the self-test clone); bare-SHA fetching is verified live, hidden `refs/pull/N/merge` tips included (GitHub's allowTipSHA1InWant). The facts ride step env with no emptiness guard — an empty SHA fails loudly inside git itself. Then `checkout` with values only: `ref` (optional — the rebase job spells the frozen payload head `github.event.pull_request.head.sha`, bypassing it; every other call site omits it and the composite spells the candidate ref `refs/heads/candidate/{N}` directly, interpolating `github.event.pull_request.number` — the rebase job has pushed the candidate ref by `needs` order, so there is no probe and no fallback; an absent side ref fails loudly inside actions/checkout) plus checkout's own `fetch-depth`/`fetch-tags` inputs forwarded raw (plain is the composite's defaults `1`/`false`; full is `0`/`true`; merge's tags-less full clone passes `0` and omits `fetch-tags`). The composite is a leaf: no toolkit clone, no uv — jobs that run binding verbs spell `toolkit-checkout` and `setup-uv` themselves, and the self-hosted unity legs never touch the toolkit at all. No `ref` threading anywhere downstream of the rebase job: no job outputs, no required inputs, no fallback chains. Composite inputs are typed (`type: number`/`type: boolean`) — actionlint never parses these files (it cannot resolve `$/`), so the old untyped-string constraint is void. Then `setup-uv` (`save-cache` input — preflight is the only saver): the composite no longer installs anything itself, so every job that needs uv spells it — the relays (`retry`, `cleanup-pr-releases`), the rebase job, and every reusable whose verbs run (mirror, preflight, the getters, the build legs, `release-pr-builds`, merge). Binding verbs then run as `uv run --project "${{ runner.temp }}/github-actions-toolkit" --locked --no-dev <verb>` with cwd = the consumer root (`--project`, not `--directory` — `--directory` would chdir into the clone and break relative config resolution). The release composites self-install the same way off `${{ github.action_path }}/../..` — the runner's action archive download IS the install, no clone step.

Domain verbs (unity-devkit's `build-unity`/matrix verbs, boatyard's `build`/`mirror`/`docker-build-matrix`, python-devkit's `preflight-python`) are different: they are dev-group dependencies of the consumer, so they run against the consumer's synced workspace as `uv run --locked <verb>` — boatyard's as `uv run --locked boatyard <verb>`, the console-script prefix — and the consumer's `uv.lock` is their version surface. `--locked` is universal law across both buses: a consumer lock out of date with its pyproject fails loudly at the first `uv run`, instead of uv re-resolving ephemerally on the runner — the committed lock is the certified version surface, never a suggestion. Structure is pinned by the `@sha` on the `uses:` ref; code by the consumer's lock.

The invocation grammar is env-indirection, and it is standing law inside every devkit-owned file: attacker-controllable expressions a `run:` step consumes (matrix values composed from the PR head tree, `needs.*.outputs.*`, workflow inputs) ride the step `env` block with the run line referencing the variable — bash parses the literal script before parameter expansion, so tainted text arrives only as word content, never as operators (zizmor's template-injection remediation). Known-immutable contexts may interpolate directly: `github.event.pull_request.head.sha`, `github.event.pull_request.number`, `github.sha`, `github.repository`; runner-controlled constants (`runner.temp`, `github.action_path`) likewise. Secrets (`GITHUB_TOKEN`, `UNITY_*`) ride step or job env, never run lines. GitHub-provided facts come from ambient runner env (`GITHUB_REPOSITORY`, `GITHUB_ACTOR`, `GITHUB_WORKSPACE`, `GITHUB_REF`), never as flags; `--config` is the local-run escape hatch. Verb output must stream live in the run log: every reusable that runs python carries top-level `env: {PYTHONUNBUFFERED: "1"}`, and the release composite carries it per-step (composites cannot set workflow-level env) — python block-buffers piped stdout, which hides prints until process exit; local terminal runs are already line-buffered.

The domain matrix verbs emit bare leg candidate lists on stdout; the binding pipes them through `matrix`, which composes the final fanout. Legs carry only per-leg-varying facts: each leg carrying a `project` key is resolved to its owning app (`apps.{name}.builds[].project` matched against the leg's `project`) and stamped with `version` (the bare `{next_version}` base — the same `next_version`/tag math the release verb uses; the domain devkits stay version-blind); legs without a `project` key (docker) and legs whose project no app owns pass untouched — unversioned builds are a supported mode — and compile-check legs carry the stamp inertly. `matrix` emits exactly one thing: the `{"include": …}` envelope as a `matrix=` line to `$GITHUB_OUTPUT`, guarding the empty-leg case loudly (an empty fanout fails in the getter, never at `fromJson` render time). Run-wide facts never ride the matrix and never enter the verb — a matrix include entry carrying a constant across all legs lies about cardinality: the unity license cache key is derived once per run by the getter calling the domain verb `unity-license-tag` (the daily UTC `v-` tag; grammar stays domain-owned), and `commit-count` is the repo-wide `git rev-list --count HEAD` derived by the getter's own count step. The fanout threads base and ordinal to the build verb as separate facts (`--version`, `--commit-count`) — no YAML composes anything. The verb renders the pair: `bundleVersion = {version}+{commit-count}` and `AndroidBundleVersionCode = commit-count` from one input pair, so the string and the integer cannot disagree. Rendering is not deriving — the binding derives both facts, the domain renders both fields.

## Consumption model (no publication)

Nothing is ever published from this repo — no PyPI wheel/sdist, no Release assets, no version tags. The commit history is the changelog; consumers pin by full commit SHA, and "what changed since our pin" is `git log <old>..<new>`. The committed `pyproject.toml` version is permanently the `0.0.0.dev0` sentinel. Bumping a consumer means changing the SHA in its `uses:` refs — all of them, to one SHA, enforced by the lint. The pinned SHA must exist on the remote before consumer CI runs, so this repo's branch is always pushed first. Pushes, pulls, and PRs are operator-owned — the agent asks, never executes; this repo's remote stays SSH, never HTTPS.

Its own `_integrate.yml` declares the four PR wakes (`pull_request: [opened, synchronize, reopened, labeled]` to `dev`) and self-consumes the whole merge machinery through `$/` calls — `rebase`, `preflight`, a terminal `merge-if-ready` — the consumer shape exactly, superseding the 2026-10-11 operator-direct ruling: the repo dogs its own merge system, every merge here exercising the same machinery every consumer gets. Its retry entry: the reusable is `retry.yml` (like `rebase.yml` and `merge-if-ready.yml` beside it) and this repo's own shim is `_retry.yml` calling it — a dispatch shim and a reusable cannot share a filename, and the underscore prefix keeps them apart, so the merge-if-ready call passes `retry-workflow: _retry.yml` while the reusable's default `retry.yml` is the consumer contract. The repo's `scripts/preflight.py` runs the python test suite plus the self-check: a dynamic clone of this repo at the workspace HEAD into `$RUNNER_TEMP/github-actions-toolkit-self-test` (hand-spelled clone — `uses:` refs cannot carry context expressions, and the head is the SHA that would merge, not `job.workflow_sha`'s merge ref), then the canonical `validate-release-plan`, `rebase --dry-run`, `retry --dry-run`, and `merge-if-ready --dry-run` run steps with cwd = this checkout, the consumer geometry exactly — the dry-run proves the full merge machinery side-effect-free at the exact SHA that would merge. Its own reusables are pure `workflow_call` files — no triggers of their own, no top-level concurrency: one file, one role. The caller owns wake triggers and serialization everywhere, and a called workflow declaring a concurrency group that meets the caller's cancels the call as a deadlock before any job starts. This repo's own merges run through the machinery itself: a workflow cannot `uses:` itself, but a repo consumes its own reusables through the same-repo `$/` call — the shape `integrate.yml` makes for rebase, preflight, and merge.

## Commands

One console script per verb — script names and flags are public API (stable-CLI-API doctrine: the YAML surface every consumer writes names them).

| Command | Role |
|---|---|
| `release` | The one delivery verb; `--channel pr\|dev\|stable` selects the mode. Every channel cuts one release per run through the same shape: draft → upload assets → publish → read back tag-form asset URLs → write notes. **stable**: compute the plan from version tags + path-diff, publish every changed package, bump and tag app versions, push per-package tags, cut the CalVer full release (latest), then sweep every `dev-*` release with tag cleanup. **dev**: publish immutable prereleases of every path-diff-changed package, cut the `dev-{count}` prerelease (count at the certified head; title `dev build {count} · PR #N: {title}` from the merged PR, or `dev build {count} · {short_sha}` when no PR merged here). **pr**: pull each app's build artifacts from the ghcr builds shelf at HEAD (the PR head) and attach them as `{stem}-{count}.{ext}` assets to the `pr-{N}-{count}` prerelease (title `PR #N · {short_sha} · build {count}`), then — once that release is fully published and noted — sweep the PR's superseded builds, every `pr-{N}-{c}` with `c` below the run's count, so one prerelease per PR stays live. The PR number parses from `GITHUB_REF` (`refs/pull/{N}/merge`) and the checkout is the ambient candidate — the candidate ref the rebase job pushed. Every pr run stages every app — no unchanged-skip. Runs with nothing to ship create no release (no apps and no built images on pr; nothing path-diff-changed plus no apps and no built images on dev; stable's nothing-to-ship early return). A re-run of the same run finds its already-published release (same SHA ⇒ same tag) and rewrites the notes only — never uploads onto a published release — and the pr sweep fires on re-runs too, healing an interrupted one. The verb appends a run summary — the release URL and one link per asset — to `$GITHUB_STEP_SUMMARY` when the variable is set. |
| `validate-release-plan` | Run the shared plan core (`load_config` → `resolve_edges` → `compute_plan` → app-version math). No flags, no env, no writes, no output. Runs as preflight's second step, after lint. |
| `lint-workflows` | Four layers, in one pass over the found files (`.github/workflows/*.yml` plus every `.github/actions/**/action.yml`): **actionlint** and **zizmor** (both fetched as pinned, sha256-verified release binaries by the verb itself — zizmor's expected hashes are constants in this repo; offline persona, plain format, config committed beside the runner, audit input the repo root so composite actions are covered); actionlint runs with five `-ignore` bridge flags — two for `job.workflow_*` (rhysd/actionlint#696/#707; dormant since the contexts moved inside `toolkit-checkout`, kept for any future raw spelling), two for the `$/` spelling (rhysd/actionlint#732; anchored on `$/` so `./`-ref and remote-format errors stay live), and one for the concurrency `queue` key (actionlint's schema predates it; the merge queue spells it) — riding until the ACTIONLINT_VERSION pin moves past the fixes; **the SHA law** — every `uses:` ref to this repository (workflow or action) is a full 40-hex SHA, all such refs in one repo carry the same SHA, and within-file YAML anchors (scalars and whole nodes alike) are sanctioned — YAML resolves them before the lint sees values; **the concurrency contracts** — `release.yml`'s group is `release-${{ github.ref }}` with no cancel (the delivery mutex), `integrate.yml`'s wake is `pull_request: [opened, synchronize, reopened, labeled]` to `dev` with no `workflow_run` and group `integrate-${{ github.ref }}` with `cancel-in-progress` (a newer wake supersedes the stale attempt), and `retry.yml` declares the retry dispatch entry — `workflow_dispatch` with required input `run-id` (number) — and `integrate.yml`'s merge-calling job runs under concurrency group `merge` with `queue: max` (one merge at a time — the rebase-merge API has no non-fast-forward rejection, so the queue is the mutex). Found-file model: filename-keyed contracts for `release.yml`/`integrate.yml`/`retry.yml`, applying to found files that do not declare `workflow_call` and normalizing a leading `_` away first (this repo's own top-level files carry the prefix) (those are consumers' top-level files; this repo's own `_integrate.yml` carries the same wake — it carries the full merge machinery through `$/` calls, so both its wake and its merge queue validate); this repo's own `_retry.yml` is the dispatch shim (the contract applies to it), and its `retry.yml` is the reusable); a found file declaring `workflow_call` is a reusable and must declare it as its only trigger with no top-level concurrency (caller-owned serialization — a group matching the caller's self-deadlocks the call); every other found file gets the SHA law only; a missing file means no contract applies — a consumer that carries no `retry.yml` learns it at the terminal's first dev-moved dispatch, a loud red with the standing re-label repair. No style rules (taste is not lint); the old grammar (verb specs, ref laws, wrapper validation, env-reference resolution, one-saver-cache, the nuget env law) died with the single-copy reusables — structure cannot drift when it lives in one place. |
| `rebase` | The head job of every integrate run (see Merging changes): no identity flag — the PR number parses from the ambient `GITHUB_REF`, and the checkout (the frozen payload head, spelled by the rebase job) is the commit identity. Fetch the current `dev` tip, rebase the head onto it (conflict → abort with the conflicted paths; the human rebases and pushes, the `synchronize` wake re-enters), force-push `refs/heads/candidate/{N}` under the job token. No label gate exists upstream of the terminal — unlabeled pushes rebase and push a candidate ref nobody consumes; the closed-PR sweep deletes it. `--dry-run` exercises the whole machinery with zero side effects: precondition failures print as informational while machinery failures still fail loudly. |
| `merge-if-ready` | The merge half of the machinery, the integrate run's success-gated terminal step (red runs never reach the verb — the red attempt renders natively in the PR checks tab): no flags — the PR number from the ambient `GITHUB_REF`, the merge lease pinned at `PR_HEAD_SHA` (the frozen payload head, threaded by the caller from `github.event.pull_request.head.sha`), the attempt counter the ambient `GITHUB_RUN_ATTEMPT`. A closed PR and an absent label exit quiet (unlabeled WIP runs must stay green); a PR head that moved from the payload aborts loudly (the lease; the abort message is the standing re-poke instruction); `dev` moved → dispatch the consumer's retry shim with this run's id (`gh workflow run {shim} --ref dev -f run-id={GITHUB_RUN_ID}`; the shim filename rides the merge-if-ready reusable's `retry-workflow` input, default `retry.yml`, threaded as `RETRY_WORKFLOW` env — this repo's shim is `_retry.yml`) and exit green — the next attempt's rebase job re-rebases; past 3 attempts, a loud re-poke with no dispatch; otherwise merge: tag `refs/tags/certified/{N}` at the tested candidate, call the pull-request merge API (`merge_method: rebase`, the lease as `sha` — GitHub replays the certified commits and never writes a human branch), verify the merged tree, delete the candidate ref and head branch, sweep `pr-{N}-*`, promote the cache; an API refusal maps by re-reading live state (head moved → re-poke; `dev` moved → re-poke; unknown → loud). `--dry-run` as above. The PR model, the policy constants, and the merge sequence live in the verb; the shared surface is `refs.py` — the PR-number ref grammar, the candidate-ref grammar, and the token-authenticated git plumbing (`FETCH_DEV_COMMAND`) — which the release and cleanup verbs also consume. Each merge verb runs from its own reusable (`rebase.yml`, `merge-if-ready.yml`) with its own env contract. |
| `retry` | The rerun relay: poll `GET /actions/runs/{RUN_ID}` until the run completes (the rerun API refuses an in-flight run — a run re-requesting itself gets a 403), then `POST /runs/{id}/rerun` and exit. Attempt N+1 of the same run re-rebases, re-tests, and re-judges, fully PR-associated: native checks-tab entries, per-attempt logs, latest attempt winning per check name, the original workflow file version and triggering actor's privileges. `RUN_ID` rides step env from the consumer's `retry.yml` dispatch input. `--dry-run` fetches the run once and reports. |
| `cleanup-pr-releases` | The closed-PR sweep: delete every `pr-{N}-*` release with `--cleanup-tag` and the candidate ref `refs/heads/candidate/{N}` for `--pr-number <N>` (an absent ref a no-op). Idempotent — absent releases are a no-op. Runs from `cleanup-pr-releases.yml` on every pull_request close, merged or not — manual merges (the GitHub merge button) bypass the machinery's sweep, and the sweep covers both paths. |
| `matrix` | stdin bare leg list (JSON array of objects) → per-leg base-version stamping → `{"include": …}` envelope → single `matrix=` line to `$GITHUB_OUTPUT` (stdout when unset). A leg carrying `project` resolves its owning app via the config (`apps.{name}.builds[].project`) and gets `version` (the bare `{next_version}` from that app's `major_minor` + `{app}-v*` tags) injected — the only per-leg stamp, since versions vary by owning app. The same `next_version` `release` will tag, so the build-time base matches the eventual release tag — this tool owns version derivation, build tools own stamping; the `+{count}` build suffix is composed by the build verb from the two facts threaded to it, never by this verb or any YAML. Legs without a `project` key (docker) or with an unowned project pass untouched; compile-check legs get the stamp inertly. An empty or malformed list is a loud failure — the getter dies before any fanout renders `fromJson`; `--allow-empty` relaxes the empty case to an empty envelope for gated fanouts (a leg set the consumer's own config derives, where empty means "not this repo"). `--key` renames the envelope's output key (job-output naming at the call site). Runs in every getter, piped after the domain matrix verb (`build-unity-matrix \| matrix`). |
| `free-disk-space` | Runner provisioning pre-step (flags `--large-packages`, `--docker-images`, `--swap-storage`): removes preinstalled toolchains/packages/images that crowd build runners. Absorbed from ci-devkit's `setup`; `build-docker.yml` gates it behind the `free_disk_space` input. |

No verb takes a flag naming the commit it acts on — the checkout is the commit identity (`merge-if-ready`'s lease pins at `PR_HEAD_SHA`, the frozen payload head; it selects nothing): `release` on the dev and stable channels reads HEAD and resolves the merged PR through the GitHub API (`commits/{sha}/pulls`, the merged PR whose merge commit is HEAD), taking that PR's certified SHA — the `certified/{N}` tag when the machinery cut one (the rebase-merge replay leaves the PR head unreplayed, so the tag names the tested tree), else the PR's head — merge-method-independent, so bot merges, UI merges, squash merges, and rebase merges all resolve identically; a certified head outside the clone's history is fetched then from `refs/pull/{N}/head`, and a merge with no PR at all (direct push) degrades to HEAD facts and a PR-less title. `matrix` and `release` on the pr channel run where HEAD already is the candidate (the candidate ref).

## The workflow contract

The binding owns workflow MECHANICS; the consumer owns triggers, concurrency, permissions, the job graph, and secret forwarding. What follows is the law for the consumer-side residue (formatting retained, not reformed: blank lines between jobs and top-level keys, permissions and secrets as block maps, job key order `needs`, `permissions`, `uses`, `with`, `secrets`). No devkit-owned file carries YAML anchors (GitHub resolves anchors server-side and aliases cannot cross files; the trio's whole-step anchors died with the `$/` composites). Merge keys (`<<:`) are forbidden — GitHub's anchor support does not implement them (silently rejected, or worse, a bogus key in loose-key maps) — should repetition ever warrant anchors again.

Composites are leaves, and the layering is law: a composite input may carry values (a ref, a key, a channel name, a boolean forwarded raw to a typed action input), never select structure — a composite needing two shapes becomes two composites and the caller spells the choice as a reference; `if:` conditionals are legitimate only on typed `workflow_call` inputs in workflow YAML (build-docker's `free_disk_space` gating the free-disk-space verb step is the shape); and no bash guard validates a spelling — a value that must not be silently wrong fails in its own consumer. Two platform walls enforce the shape. The `secrets` context is withheld from composite actions entirely — a parse failure (`Unrecognized named-value: 'secrets'`), not an empty string (github/docs#12705) — and is unavailable in `if:` conditions even in workflows, so a secret crosses only as a workflow-context expression. And `./` local `uses:` inside a composite resolves against the consumer's workspace, not the action's own checkout (actions/runner#1348), so a composite cannot reference its siblings via `./` — the `$/` self-repository reference is the fix and is in use for the install trio; the release composites nonetheless stay self-contained (their sibling-prelude dedup via `$/` is possible but not done, the duplicated prelude the accepted price).

- `integrate.yml` is the whole merge machinery, woken by `pull_request: [opened, synchronize, reopened, labeled]` to `dev` under `integrate-${{ github.ref }}` with cancel-in-progress (a newer wake supersedes the stale attempt; re-runs hold their place — concurrency is not re-evaluated). It composes `uses:` calls in one chain: `rebase` (the head job, `permissions: contents: write, pull-requests: read` — the candidate-ref push rides the job token), then `mirror-images` (where images exist; provisioning precedes consumption, and its long-term destiny is hermeticity enforcement), then `preflight` (needs rebase/mirror), then the build legs (needs preflight), then `release-pr-builds` (needs the terminal build legs), then a terminal `merge-if-ready` job (`needs: [release-pr-builds]`, success-gated by default — red runs never reach the verb — under `concurrency: { group: merge, queue: max }` — the global merge queue, one merge at a time — forwarding only the merge-bot secret). A calling job accepts only `needs`, `if`, `permissions`, `with`, `secrets`, `strategy`, `concurrency`, `name` — never `steps` (that is what "use the reusable" means).
- `retry.yml` (consumer) is the retry dispatch target, lint-mandated: `workflow_dispatch` with required input `run-id` (number), `permissions: actions: write` (the rerun call rides the dispatch run's own token — the consumer run's context is the natural holder of that grant), and one `uses:` call to this repo's `retry.yml`. Every dispatch target is a thin consumer shim plus a toolkit reusable; the terminal's dispatch addresses it at `--ref dev`, where the shim exists for every adopter — the rerun replays the original run's frozen workflow version and payload regardless.
- This repo's own top-level workflows carry a leading underscore — `_integrate.yml`, `_retry.yml`, `_cleanup-pr-releases.yml` — so they read as this repo's own rather than more reusables beside them: GitHub discovers workflows only as direct files of `.github/workflows` (no subdirectories), so naming is the only separator, and the lint normalizes the prefix before contract matching. The `_cleanup` shim is the closed-PR sweep, this repo's own consumer of `cleanup-pr-releases.yml`, and the only repo-specific file consumers never need (they spell the same wake themselves).
- `cleanup-pr-releases.yml` (consumer) is triggers (`on: pull_request: [closed]`) + permissions + one `uses:` call to this repo's `cleanup-pr-releases.yml` — input `pr-number: ${{ github.event.pull_request.number }}`, `permissions: contents: write`, no `if:` gate: the sweep runs on every close, merged or not, because manual merges bypass the machinery's sweep and the sweep is idempotent. The trigger stays consumer-owned per the workflow contract; the reusable is mechanics-only (`workflow_call`, no top-level concurrency).
- `release.yml` stays ONE file for both channels: npm allows one trusted publisher per package, bound to a single workflow filename — a split would leave one channel unpublishable — and nuget.org binds owner/repo + workflow filename the same way, so `release.yml` must never be renamed. Its concurrency (`release-${{ github.ref }}`, NO cancel) is a queue and the policy: the `main` group is the release mutex, and the serialization makes the CalVer count-and-cut and the `dev-*` sweep safe. Delivery jobs are one `uses:` of the release composite each, the channel spelled as the composite's required string input (`channel: stable` for the stable job, `channel: dev` for dev) — the composite runs inline in the caller's job, so `job_workflow_ref` keeps naming the consumer's `release.yml` (warehouse#11096 blocks reusable-workflow publishers, not composites). The composite absorbs the checkout/no-ref/tag-fetch law (credentials persist for the tag push only on stable, via `persist-credentials: ${{ inputs.channel == 'stable' }}` — string equality, no coercion), setup-uv, the NuGet login, and the verb invocation (`RELEASE_CHANNEL: ${{ inputs.channel }}` riding step env — pure value forwarding, the run line referencing the variable). Channel-input law, from two live failures on the boolean form: booleans never cross into expression evaluation inside a composite — inputs arrive stringified inside `${{ }}`, where a bare truthiness test reads `"false"` as true and an `== true` comparison number-casts `"true"` away from boolean true (each failure verified live on the opposite channel) — while strings cross safely, forwarded as values or compared as strings. A wrong channel value dies at typer's Choice parse before any side effect, and `persist-credentials` computes false for anything but the exact `stable` spelling — a garbage run never holds push creds. NuGet routing is the presence of the repo secret: the consumer maps `NUGET_USER` once in workflow-level env (`env: {NUGET_USER: ${{ secrets.NUGET_USER }}}` — one line serves both delivery jobs, the only sanctioned secret crossing into composite-land), the composite gates the login on `env.NUGET_USER != ''` and feeds the minted `NUGET_API_KEY` to the verb env. `NUGET_USER` is a per-repo secret, never org-level — org secrets are visible to every repo and would switch the login on fleet-wide.
- `workflow_run` is banned outright — zizmor's dangerous-triggers audit fires on it and no relaxation remains. The machinery's wakes are the four `pull_request` activities, and retries are re-runs of the same run (a run the machinery owns needs no doorbell) — the label is state, not an event: standing intent the terminal carries to the merge with no re-click ceremonies for pushes, failures, or rebases. Nothing waits on the PR's own checks: GitHub's recursion guard suppresses `check_run`/`check_suite` for Actions-created checks, and the run IS the certificate — the checks tab is demoted from evidence to convenience.
- Jobs never `needs` across the file boundary — verification certifies on PRs, delivery runs on the merge push.
- Job `permissions:` are consumer-owned: mirror/build legs carry `contents: read, packages: write`; `release-pr-builds` carries `contents: write, packages: read` (release writes, shelf pulls); `cleanup-pr-releases` carries `contents: write`; delivery jobs carry `contents: write, id-token: write` (trusted publishing), `pull-requests: read` (dev/stable resolve the merged PR through `commits/{sha}/pulls`, which a private repository serves only under that grant — a public one serves it anonymously, masking the gap until the first private consumer), plus `packages: read` (prerelease shelf pulls) or `packages: write` (stable, where apps pull the shelf); the rebase call carries `contents: write` (the candidate-ref push rides the job token) and `pull-requests: read`; the terminal merge call carries `contents: write`, `pull-requests: read`, and `packages: write` — every dev write rides the minted App token, while the cache promotion authenticates as `GITHUB_TOKEN` through the neutral `REGISTRY_*` env chain (the merge-bot App holds no packages grant, and a called workflow can only downgrade its caller's grant, so the reusable and every call site spell both scopes). Fork PRs are out of scope: their runs carry no secrets and fail red at the first checkout — the candidate ref never exists for them — and the fork lane (`plan-fork-pr-landing.md`, workspace root) is the follow-up that brings them in.
- The preflight script contract: a required Python script at the repo-root path `scripts/preflight.py`, invoked by the harness as `uv run --locked scripts/preflight.py` (no shebang, no executable bit), missing file a loud red — never a skip. The `consumer-script` input (typed boolean, default true) is the declared escape for repos with no Python: the call site spells `consumer-script: false` and the repo carries no script, pyproject test suite, or ruff files — the opt-out is explicit at the call site, so a Python repo losing its script can never be a silent skip. The harness (this repo's `preflight.yml`) provides checkout at the candidate (full fetch), uv, docker on the runner, cwd = the repo root, and `GITHUB_TOKEN` in the step env; exit code is the whole interface. Per-consumer variance (e.g. `packages: read` for a preflight that pulls mirrored images) rides the calling job's permissions.
- Unity build legs: `runs-on: ${{ fromJSON(inputs.runs-on) }}` — the reusable's `runs-on` input is a JSON array string of runner labels, default `["ubuntu-latest"]` (the hosted default; GitHub has no comma-splitting in `runs-on`, so an array string through `fromJSON` is the only multi-label spelling an input can carry — a self-hosted consumer spells e.g. `["self-hosted", "unity"]`), the `unity-environment` input (string, default empty) is build-time config-flavor selection, the consumer's build policy: it rides the leg's step env and the run line as `--environment-preset`, which playerbuild materializes as the shipped `UnityEnv` preset (empty leaves the workspace untouched), `container: ${{ matrix.editor-image }}`, a wipe-workspace first step (inert on hosted, load-bearing where runners are reused), a git safe-directory pre-step (the container user differs from the workspace owner; the build verb's `git rev-parse HEAD`, which derives the `sha-{full}` shelf tag, needs the trust), license threading via named `unity-email`/`unity-password`/`unity-serial` call-site secrets, Android signing via the required `android-keystore` (base64 file)/`android-keystore-password`/`android-key-alias`/`android-key-password` call-site secrets — every consumer MUST provision them: the leg decodes the keystore to a runner-temp file and hands the quartet to the build as `KEYSTORE_*` step env, which the playerbuild entry applies to `PlayerSettings.Android` (required, not optional, because an unprovisioned consumer would silently sign every build with a fresh per-runner debug keystore and churn the app's Android signing identity; the in-script emptiness guard in the decode step is belt-and-braces against empty-string forwarding), and registry auth as `REGISTRY`/`REGISTRY_TOKEN`/`REGISTRY_USERNAME` step env (the `CI_` prefix is dead — the docker contract always spelled it this way). The leg schema (which keys a domain verb emits: `project`, `platform`, `editor-image`) is named contract with the domain devkits — renaming a key breaks this repo's fanout YAML; `version` is binding-injected by `matrix`, never domain-emitted. Run-wide facts reach the fanout as getter job outputs, each derived by its own single-output step — the license cache key (the getter calls `unity-license-tag` once; the domain verb flag that consumes it is `--license-cache-key`, named for what it is: the ORAS tag the license cache restores under, not a license) and `commit-count` (a plain `git rev-list --count HEAD` count step) — never as leg keys. The leg's step env carries every fact grouped by source — the leg's matrix facts (project, platform, version), the event fact (pr-number), the run-wide getter outputs (commit-count, license cache key), the call-site input (unity-environment), the unity secrets, the keystore quartet (keystore path, keystore password, key alias, key alias password), the registry trio (registry, registry token, registry username) last — and the run line's switches follow that same order with the secrets elided (`--project`, `--platform`, `--version`, `--pr-number`, `--commit-count`, `--license-cache-key`, `--environment-preset`, `--registry`): one source order everywhere. `build-unity` takes no mode switch — shelving (the build-output push plus the CI cache bundle) is implied by the supplied registry env, which the binding always supplies; absent registry env is the local build. The build verb composes `bundleVersion = {version}+{commit-count}` and stamps `AndroidBundleVersionCode = commit-count` from that one input pair — rendering, not deriving, so the string and the integer cannot disagree. The getters are named for their role (`plan-unity-builds`, `plan-unity-compile-checks`, `plan-docker-builds`), not for the transport format they emit.
- Docker build legs: matrix values env-indirected in `run:` lines; QEMU arm64 + buildx setup live inside `build-docker.yml`; `free_disk_space` is a reusable input, not a domain config key. The domain verb runs `build --push` with explicit parameters — registry, actor, and token supplied by the binding via step env (`REGISTRY`, `REGISTRY_TOKEN`, `REGISTRY_USERNAME`), never ambient `GITHUB_*` reads in domain code. A repo whose images carry their own compose wiring ships it through the same reusable: the getter also pipes `publish-compose --plan` (boatyard) through `matrix --allow-empty`, and the `publish-compose` job — `if`-gated on that plan being non-empty, `needs` the build matrix — runs the domain verb with `--branch` and the registry env; the section in `boatyard.yml` is the single declaration of bundle shipping, the call site adds nothing. The getter also gates score-artifact staleness: one step runs `uv run --locked boatyard generate-score --check` — a repo whose committed score artifacts no longer match its `stack/score/` sources fails the getter, printing the drift, before any fanout leg starts (the artifacts are the assembly's structural surface — namespaced services, tree slots, baked lock digests — so a source change without regeneration ships the previous assembly shape); a config declaring no local service entries and no `k8s:` section self-skips (exit 0, the `matrix --allow-empty` pattern, owned by boatyard). The getter also gates lock freshness: one step runs `uv run --locked boatyard lock --check` (the `uv lock --check` analog, owned by boatyard) — the relock computes in memory and a stale committed lock fails the getter printing the unified diff, so the binding carries zero lock-path knowledge; a declaration change without a relock fails the getter instead of shipping a silent no-op bump; the verb self-skips where no lock declarations exist (no `base_images`, no `k8s.charts` — the same self-skip pattern, owned by boatyard). A domain check riding the domain's binding surface — an input invariant of the build/publish path this reusable composes, not a preflight concern. Both getters pipe through `matrix --allow-empty` and both fanout jobs are `if`-gated on their envelope being non-empty (`fromJSON(...).include[0] != null`) — both leg sets are consumer-config-derived, where empty means "not this repo": a mirror-only repo (`base_images` declared, no root `repository` — zero build legs) sees `build-docker` skip, a repo with no `publish-compose:` section sees `publish-compose` skip, nothing else changes. The compose gate rides `${{ !cancelled() && !failure() && … }}` — a skipped `build-docker` must not take the bundle publish down with it (the zero-build bundle repo is the exact case), while a failed build leg still blocks the publish.
- Comments in devkit-owned files are minimal and end without a period; step `name:` survives only when it says something the command does not.

## Merging changes (the bors model)

`dev` is evergreen: nothing merges onto it whose tree was not certified green on the exact `dev` tip it merges against — the merge replays the certified commits through GitHub's rebase-merge API, so the merged SHAs are the forge's mint and the certified trees are ours (`adr-api-rebase-merge-landing.md`). This repo merges through the machinery itself (superseding the 2026-10-11 operator-direct ruling): its own `_integrate.yml` carries the consumer shape through `$/` calls, so every merge here exercises the same machinery every consumer gets. Push a branch, open a PR to `dev`, apply the `ready-to-merge` label whenever ready — the label is state, not an event: one click at any time eventually merges the PR, with no re-click ceremonies for pushes, failures, or rebases. Recovery from a red test suite is "fix, push" — the `synchronize` wake mints a fresh run with a fresh rerun budget.

One workflow, one loop, one merge authority: the consumer's `integrate.yml` is the whole merge machinery (`adr-integrate-rerun-lander.md`; the evaluator verb and the fast path are deleted — merging on a checks-tab photograph was the one act this architecture exists to prevent). The run is the certificate: nothing merges on a read, nothing machine-reads the checks tab, and the `evergreen-dev` ruleset (merge-bot bypass only) keeps humans from acting on it. The machinery owns a candidate ref, `refs/heads/candidate/{N}`. Four wakes feed one chain — `opened`, `synchronize`, `reopened`, `labeled` (all to `dev`) — and every run is a candidate merge: the `rebase` job resolves the PR number from the ambient `GITHUB_REF`, rebases the frozen payload head onto the current `dev` tip (conflict → abort with the conflicted paths; the human rebases and pushes) and force-pushes the candidate ref, which every downstream job checks out ambiently through `checkout`. There is no label gate upstream of the terminal: unlabeled pushes run the suite, rebase, and push a candidate ref nobody consumes; the closed-PR sweep deletes it.

The terminal `merge-if-ready` job (success-gated — it runs only when the suite passed; red attempts render natively in the PR checks tab and never reach it) runs the verb, which applies the policy in order: a closed PR and a withdrawn label exit quiet; a PR head that moved from the frozen payload aborts loudly (the lease, live `gh pr view` against the payload — freshness never reads the payload for liveness); `dev` moved → dispatch the consumer's `retry.yml` with this run's id and exit green (the next attempt's own rebase job re-rebases; past 3 attempts, a loud re-poke with no dispatch); otherwise merge: tag the tested candidate as `refs/tags/certified/{N}`, call the pull-request merge API with `merge_method: rebase` and the lease as `sha` (GitHub replays the certified commits onto `dev` itself — no write to any human branch — and closes the PR as **Merged** with full attribution), verify the merged `dev` tree equals the certified candidate (the race alarm), delete the candidate ref and head branch, sweep the PR's `pr-{N}-*` releases with tag cleanup, and promote the PR's unity library cache onto the dev tag. The merge push fires `release.yml`. The certified-head welds key at the tagged candidate: the release resolves `certified/{N}` (the PR head stays the unreplayed original and `dev`'s tip is the forge's replay — neither is the tested SHA), the builds shelf keys `sha-{full}` at the run's head — the candidate-ref tip the tag points at — commit-count ordinals derive there, and promotion's tree equality is the verified alarm itself.

Merges serialize through one global merge queue: the consumer's terminal `merge-if-ready` job runs under `concurrency: { group: merge, queue: max }` (lint-enforced on the calling job — the documented placement for reusable calls), so at most one terminal holds the merge window at a time. The `evergreen-dev` ruleset's merge-bot-only bypass makes the machinery the only writer of `dev`, the queue is the mutex over those writers, and the terminal's dev-moved check inside the queued job is the compare — the rebase-merge API has no non-fast-forward rejection to serialize for us, and the post-merge tree verify alarms on the race a silent API would hide. An API refusal maps by re-reading live state (head moved → re-poke; `dev` moved → re-poke; anything else → loud) — gh hides the HTTP status, so state names the branch, never the error body.

Retries are re-runs of the same PR-associated run: re-runs replay the frozen original event payload (same `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT` incremented) and stay fully PR-associated — native checks-tab entries, per-attempt logs, latest attempt winning per check name, the original workflow file version and triggering actor's privileges. The frozen payload corollary: `github.event.pull_request.head.sha` does not update on later attempts, which is exactly the lease; freshness checks read live state, never the payload. Limits (50 re-runs per run — fresh budget per push, a 30-day window, full re-execution of all jobs per attempt) and the accepted costs (every merge pays one full suite; O(N²) runner-time under contention — the max-3 bound hands timing back to humans; the checks-tab marks pin to the payload head while the tested tree is the rebased candidate, cosmetic since nothing machine-reads the marks) are recorded in the ADR. No cron: the wake set is complete, and a lost wake — a failed retry dispatch among them — is repaired by the same human move as ever (re-apply the label).

The promotion is best-effort suffix-swapping in `promote_scope` (build-artifact-registry): every tag ending `-pr-{N}` on `{registry}/cache/unity-library` is aliased onto the `-dev` spelling — same digest, `oras tag` metadata alias; the merge commit's tree equals the PR head's tree, so the promoted library is dev's new library by construction. The tag grammar is a named contract with unity-devkit's `identity.cache_key` — a grammar change updates the binding's matcher and unity-devkit's AGENTS.md alike. A repository with no unity-library cache (non-Unity consumers) promotes nothing; a failed promotion warns and never fails the merge — the previous dev cache stands, the next merge self-heals, and a manual `oras tag` is the post-merge escape hatch (the merge verb skips a non-OPEN PR quietly on re-run). The merge bot holds the `evergreen-dev` ruleset's Integration bypass; with the ruleset active it is the only door. **Never label a PR in a repo without a live verification job** — the success-gated terminal is vacuously green on a suite that never ran.

## The CI-commit-free invariants

CI and release workflows create no commits at all — the merged commits are the forge's own rebase-merge replay, and `dev` → `main` merges are always true fast-forwards. Two regimes: **protected branches** (`dev`, `main`) hold to exactly that; **ephemeral refs** are the machinery's own — `refs/heads/candidate/{N}` and the `certified/{N}` tags, created, force-updated, and deleted at will, no ruleset, no history value. CI never writes a human branch: the candidate ref is the only branch CI pushes, and the merge itself is GitHub's API call.

- **Version tracking**: per-package git tags (`{name}-v{semver}`, e.g. `placeframe-api-client-v0.1.8`), never committed state files.
- **Change detection**: `git diff --quiet <last-tag> HEAD -- <path>`, never content hashing — or the package's declared `major_minor` sits above every existing tag, which forces the publish: a new line always ships, even when the bump rode commits that never touched the package path (the config lives at the repo root, so the bump alone is invisible to path-diff). No cascade: an unchanged dependent is an immutable, coherent pairing — UPM/npm treat declared dependency values as minimums, so a newer sibling always satisfies.
- **Version scheme**: major.minor is config data (the required `major_minor` on every package and app entry), patch is tag data: the highest stable tag within the declared line plus one patch, or `.0` when the line has no tags. A declared line below any existing tagged version fails loudly (never compute downward). Per-package numbers are independent within one release event — no lockstep.
- **Manifest version sentinels**: Unity `package.json` versions are permanently `0.0.0+local` in the repo; Python `pyproject.toml` versions permanently `0.0.0.dev0` — patched ephemerally at publish and restored immediately, never committed. The sdist/wheel carries the real version; the committed file never does.

## The dependency-edge law

Same-release-unit dependency edges are **inferred from manifests**, not authored in config: each package's manifest dependencies (package.json `dependencies` for npm, `[project].dependencies` for pypi, csproj `PackageReference` for nuget) are intersected with the config's registry identities; a match is an edge, everything else is an external dependency that ships verbatim. Edges drive topological plan ordering — dependencies-first, load-bearing for nuget, where `dotnet pack` restores the sibling from the registry — and validation only, never version selection.

Same-unit dependencies are authored as the sentinel `0.0.0+local` — one string that is valid semver (build metadata), PEP 440 (local version), and NuGet. The concrete version exists only in the published artifact, injected at publish from the event's plan: the sibling's new version if it co-publishes, its current tag if unchanged (HEAD is then byte-identical to that release), a loud error if it never published. The dev channel injects a co-publishing sibling's dev spelling (keyed on the same run count) and an unchanged sibling's current stable tag. Cross-unit and ecosystem dependencies are authored exact and shipped verbatim — adoption is a human commit.

Plan-time validations, all atomic before any registry call, all caught by `validate-release-plan`: a sentinel on a non-config identity; a real version where a config identity expects the sentinel (hard flip — staleness cannot ship); a sibling that has never published; cyclic edges.

## Dev channel

The dev channel (`release --channel dev`) publishes immutable prereleases of every path-diff-changed package and cuts the `dev-{count}` published prerelease: every package (a `Package | Registry | Version` row, the version linked to its registry page — this run's dev version when changed, latest stable tag otherwise), every app (an `App | Platform | Version` row per build entry, the version linked to the count-suffixed asset and shown as the stamped `{base}+{count}` bundleVersion the binary carries — the same next-version base the matrix verb stamped into the build, never the last tagged version), and every built image (an `Image | Tag` row per image, ordered by image ref, the `tree-` tag linked to that exact package version's page on GitHub — the digest stays one click away on that page, never a column: a 71-char unbreakable token forces the table past the release body's clip). Bodies are snapshots, not changelogs — every merge cuts one, listing all artifacts at that SHA; there is no app-level change detection in the dev channel, so each run re-pulls and re-attaches every app's shelf build at that SHA — the churn is the accepted cost of not trusting change detection. It creates no git tags, bumps no app versions. Versions are keyed on the commit count at the certified head (`git rev-list --count {sha}`, computed once per run and threaded to packages, the release tag, and asset names — the same ordinal the build verb composes into the app binaries' version strings; the certified head is the SHA the build legs built at, and counting the merged commit instead would run one ahead) and spelled per registry — `{base}.dev{count}` on PyPI, `{base}-dev.{count}` on nuget and npm; no hex SHA can ride a PyPI dev version (PEP 440's `.dev` segment must be numeric), while the count re-derives the same version idempotently on re-runs. The base is the next version derived from the declared `major_minor` and the tags, so dev versions share one base until the stable flow tags it. npm prereleases ride the single inert `dev` dist-tag so `latest` never moves.

## Per-run release surfaces

Three surfaces expose CI-built APKs and built images, all mirroring the ghcr builds shelf (which stays canonical — the unity build leg pushes player binaries and the docker build legs push digest-manifest shards there, all `sha-{full}`-keyed; `release` on every channel staples from there, merging a SHA's docker shards at pull time — the legs run in parallel, so each shelves its own `sha-{full}-{key}` shard and the merge belongs to the consumer that runs after they finish). Image tag links (verified live 2026-10-11): the browsable package page is the repo-scoped `github.com/{repo}/pkgs/container/{name}` — the historical `orgs/{org}/packages/container/...` form 500s even authenticated — and the per-version page is `{pkgs-page}/{version-id}?tag={tag}`, where the numeric id comes from the packages API (`gh api /orgs/{org}/packages/container/{name}/versions`, matched by digest — the `.name` field); an unresolved id falls back to the bare package page; the image's display name is its ref tail under `ghcr.io/{repository}/`, and a ref outside that namespace is a loud error:

- **PR build release** (`pr-{N}-{count}` tag): one published prerelease per integrate run of every publishing consumer; the run attaches a count-suffixed asset per app and lists the run's built images. `release --channel pr` writes it from `release-pr-builds.yml`. Superseded builds do not linger: once a cut is fully published and noted, the run sweeps the PR's lower-count `pr-{N}-*` releases with tag cleanup — ordered by count, so a late-finishing older run can never delete a newer run's release, and fired after publish, so a failed run leaves the previous build standing. Exactly one prerelease per PR stays live while it is open. The closed-PR sweep (`cleanup-pr-releases.yml`) removes every closed PR's releases — the machinery's own sweep after a merge, the close-triggered sweep everywhere else. The title is `PR #N · {short_sha} · build {count}`.
- **Dev build release** (`dev-{count}` tag): one published prerelease per merged PR, cut by the merge push; `release --channel stable` sweeps every `dev-*` release after cutting the CalVer release. The title is `dev build {count} · PR #N: {title}` — the channel and count lead so a dev release never reads as a PR release at a glance. The PR number and title come from the merged PR resolved through the API, so any merge method cuts the same title; a PR-less merge (direct push) degrades to `dev build {count} · {short_sha}`.
- **Main release** (CalVer `YYYY.MM.N`): `release --channel stable` cuts one asset per platform — the promoted build — and its body lists the same three artifact tables the per-run releases use, rendered by the same spine so the surfaces cannot drift.

Every channel uses one creation shape: draft → upload assets → publish (`--prerelease` on pr/dev) → read back tag-form asset URLs → write notes. A draft release can never carry working links to its own assets — GitHub serves a draft's assets under a per-release `untagged-{hex}` slug that is re-keyed when the release record is edited, unknowable before the edit — so the publish step intervenes before the read-back and the notes' links arrive in `releases/download/{tag}/{name}` form, stable forever. The draft window is also the partial-failure recovery under release immutability: a botched upload leaves a deletable draft, never a burned tag name. A re-run of the same run (same SHA ⇒ same tag) finds the published release, skips creation and upload, and rewrites the notes only — the bits are identical because the shelf is `sha-{full}`-keyed, and uploading onto a published release is forbidden under immutability anyway; the pr-channel sweep still fires, healing an interrupted one. Tag names never repeat by construction — PR numbers are unique and commit counts monotonic — so immutable-release tag burning cannot collide, and no `{name}-v*` version tag can collide either. Empty runs create nothing, computed before any release exists. The shapes are immutability-compatible: assets ride the draft window, and notes/title/prerelease/latest edits stay legal after publish.

Asset naming: pr/dev releases use `{stem}-{count}.{ext}`; the main CalVer release keeps the bare configured `file`. Asset links in body tables are read back from the published release's own asset URLs after publish, never constructed. The SHA survives only as identity, never as a version: the `sha-{full}` builds-shelf keying and the commit-link heading.

## The Registry seam

One `Registry` adapter per registry (`publishing.py`: `NuGetRegistry`, `NpmRegistry`, `PyPIRegistry`), driven by the package loop in `publish_packages` (`verbs/release.py`), each `publish(path, base_version, resolved_dependencies, dev, commit_count) -> str` — the adapter resolves the channel spelling itself and returns the version it published; adapters also own their package-page grammar (`url(identity, version)`), so release-note links ask the same seam; the adapters derive the package's registry identity from the package's own manifest, so no identity is passed. A package's registry identity is config data, not code — every package declares exactly one `registry` and its `identity` there, a required pair validated against `KNOWN_REGISTRIES` at config load; each adapter packs from its own manifest type under the package path, so one package is one ecosystem.

All three are keyless from the consumer's secret store. PyPI authenticates via trusted publishing (OIDC): the consuming job needs `id-token: write` and the project a configured (or pending) publisher; idempotent re-publishing rides `uv publish --check-url`. npm authenticates the same way (`--provenance`, no token plumbing). nuget joins through the official `NuGet/login@v1` action (pinned by SHA inside the composite), which exchanges the job's OIDC token for a ~1h API key the composite feeds the adapter; `NUGET_USER` reaches it via the workflow-level env crossing (see the workflow contract — the secrets context never enters composite-land).

## Config

`config.PublishConfig` (pydantic, `extra="forbid"` on every model) validates the root `publish.yml`, loaded strictyaml-first (duplicate keys rejected, all scalars preserved as strings — pydantic coerces per-field). Hard flips, no accept-both: an unmigrated or unknown key fails loudly at load. All keys optional — an empty document loads as the empty config; `packages` and `apps` map by name, which doubles as the git-tag prefix.

The builds shelf address is derived, never configured: `ghcr.io/{repository}/builds` from the ambient `GITHUB_REPOSITORY`. Keying law: every shelf artifact is tagged `sha-{full}` where the SHA is the certified PR-head SHA integrate built at; docker digest manifests shard per matrix leg as `sha-{full}-{key8-of-leg-targets}` (parallel legs cannot share a tag), and `pull_digest_manifest` enumerates a SHA's shards and merges, a repeated target across shards a loud failure — the pre-shard bare `sha-{full}` tag still resolves as a one-shard fallback. Apps declare their artifacts directly: `builds` is a required, non-empty list of entries carrying `project` and `platform` — the push side's exact spelling, so the pull side cannot drift from whatever pushed the shelf — and `file`, the release-facing filename. One shelf layer holds exactly one file, the build's single player binary (build reports push to their own `{project}-{platform}-report` reference); the push side guarantees it. Built images are declared by a non-empty root `repository` in the consumer's `boatyard.yml` — a named contract with boatyard — which the release verb reads as a plain-yaml presence probe (`built_images` in config.py, no boatyard import — the resolver-cycle law): mirror-only repos (`base_images` declared, no `repository`) derive False, matching their zero build legs; a repository-declaring repo with no digest-manifest shards at the certified SHA is a loud failure.

The config-file law org-wide (home: this file; siblings reference it, they don't duplicate it): config lives beside the unit whose facts it carries. A tool whose subject is the Python project configures from pyproject `[tool.<devkit>.*]` tables; every other devkit uses one root `<devkit>` YAML file per repo. python-devkit is the one pyproject-table devkit; unity-devkit the one JSON exception (read by C# inside Unity); this repo / openapi-client-codegen are root `.yaml`, boatyard root `boatyard.yml` — with this repo's consumer config the law's one exception: `publish.yml`, named for the workflow family, not the devkit.
